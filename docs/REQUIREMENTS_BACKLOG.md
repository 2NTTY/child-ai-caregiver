# REQ-001｜搜索優先的育兒資訊體驗與三類資料來源

## 1. 背景與問題

使用者不滿意目前聊天體驗：等待較久後可能只得到「未通過獨立核對」，畫面又出現「原運行仍在處理」等狀態，無法清楚知道工作是否完成、為何失敗及下一步能做甚麼。

現階段不以全面擴張助手功能為目標，先讓家長能方便地搜索、理解育兒資訊，得到有依據且有用的結果。

## 2. 已確認的產品目標

### 2.1 優先次序

- **第一目標：先完成搜索能力與使用體驗。**
- **第二目標：其後再完善代辦、成長記錄等助手功能。**
- 不要求為本需求刪除既有助手功能；具體入口安排在設計時處理。

### 2.2 搜索的用途

家長可以用日常語言提出不懂的問題，例如某種常見狀況是甚麼、為甚麼出現、有哪些處理選擇，以及相關產品有哪些資料可參考。

- 不要求家長先知道專有名詞或精確搜尋關鍵字。
- 不把所有一般、常見問題一律回覆為「去醫院」。
- 同時不能把資訊整理冒充個別診斷，或忽略需要進一步求助的情況。
- 不只是列出連結，還應讓家長理解問題、資料的適用範圍及可選擇的下一步。

### 2.3 產品資訊定位

- 可搜索及整理兒童產品資料，例如奶粉、護理用品等。
- 不做商業推薦、帶貨或宣稱某產品最好；由家長自行決定是否購買。
- 可以呈現規格、用途、差異、社群使用感受，以及有依據的樣本整理。
- 即時搜索得到的有限帖子不能直接宣稱為整體家長使用率、滿意度或代表性統計。
- 論壇發言屬使用者自述，不自動當成已驗證購買／使用經驗。

## 3. 已確認的三類資料架構

### 3.1 A 類：長期官方知識庫

**用途：回答穩定、可反覆查詢的一般知識。**

內容例子：
- 政府育兒手冊、官方照護指引、常見問題。
- 飲食、睡眠、清潔、發展、安全等基礎資訊。
- 穩定的公共服務介紹及辦理資訊；有期限的部分另歸時效資料。

核心要求：
- 建立長期資料庫及可引用的 RAG 搜索。
- 保存原文及來源，不只保存 AI 摘要。
- 定期檢查來源更新，有變更才處理，不每天重新匯入整庫。
- 官方資料變動較少，不代表永遠不檢查或自動視為最新。

### 3.2 B 類：每天檢查更新的時效資訊庫

**用途：回答近期發生甚麼、目前有哪些有效變化。**

內容例子：
- 兒童／育兒相關新聞。
- 官方健康與安全公告、產品召回、食品或奶粉安全警報。
- 政策變更、限期申請、活動及服務異動。

核心要求：
- 每天檢查，有新資訊才新增或更新；沒有就沒有，不強求每日產出。
- 無用、過時的資料退出日常搜索，按保留規則清理。
- 家長問起近期事件時，系統能查詢並回答。
- 重要且與使用者相關的事件才主動提醒，不把一般新聞全部推送。

**建議保留規則，尚待具體化：**
- 有效召回及安全警報不能只因資料較舊就刪除，應依是否解除、取代及仍適用判斷。
- 事件正文清理與保留必要狀態、來源、歷史引用是不同決策。
- 每日檢查不等於保證分鐘級即時；若需更高時效，另定來源與檢查頻率。

### 3.3 C 類：按需即時搜索

**用途：取得變動快、來源廣、不需要預先整庫保存的資料。**

內容例子：
- Baby Kingdom及其他可存取的公開家長討論。
- 產品使用感受、優缺點、不同經驗與爭議。
- 最新商品規格、價格、庫存、優惠與購買渠道。
- 服務目前的收費、名額、營業資訊及近期評價。
- 時效庫尚未收錄、但使用者剛問到的新事件。

核心要求：
- 問到才搜索、讀取相關原文並整理，不建立整個論壇的長期資料庫。
- 附上原來源及可確認的日期，不只憑搜索摘要下結論。
- 讀不到、搜索不到或結果過舊時，明確說明限制。
- 不把搜索排名或討論熱度當成品質、安全性或效果證明。
- 接入前確認平台允許的取得與使用方式，不繞過登入／存取限制。

### 3.4 分類原則

按**內容性質**分類，不把整個網站固定歸一類。政府手冊可以是長期知識，政府今天的召回公告則是時效事件。

同一問題可以合併查詢多類來源，但呈現時區分：官方依據、近期事件、社群經驗及商品資料。

## 4. 搜索體驗需求與建議

使用者已明確提出「不要長等後只有審核失敗」及「異步檢查、固定求助入口」。以下流程、畫面與恢復方式是對這些目標的建議拆解，實施時再確認具體設計。

### 4.1 基本路徑

使用者提問 → 理解問題／必要澄清 → 選擇資料來源 → 搜索及讀原文 → 整理有引用的結果 → 必要核對 → 交付。

- 只有缺少會影響答案的條件時才補問，避免每題先做冗長問卷。
- 不要求普通查詢先跑代辦、成長記錄或記憶寫入流程。
- 不要求每題都搜索所有資料來源；按問題及時效需求選擇。

**送往外部搜索的查詢只帶必要條件：**

- 這是第三方傳輸邊界，不是刪除主聊天或剝奪 Agent 已獲授權的上下文。外部 query 不直接拼上姓名、完整生日、地址、聯絡方式或整段私人對話；只傳為回答本題所需的條件，不能因內部已可讀就全部外送。
- 保留會改變答案的必要年齡／年齡段、症狀、持續時間及足夠的地區粒度等語義；例如能以年齡回答便不傳完整生日，能以地區判斷便不附完整住址。最小化不能把問題改歪，缺少必要條件才澄清；確需更多資訊時仍按原批准及實際服務契約處理，不自行擴大授權。
- 公共／私人儲存隔離不能代替這項外送控制。沿既有問題理解、工具參數組裝及必要程式檢查實現，不為每次搜索另加脫敏／意圖分類模型回合；主聊天與臨時聊天同樣適用。
- 減少識別欄位不保證匿名或不可重新識別，也不改變第三方原有保留政策；不得將「已最小化」當成可任意分享私人資料的保證。

### 4.2 等待、失敗與恢復

- 提供真實、簡短的處理進度，不用虛構百分比。
- 工具計數、技術錯誤及診斷資料可放進詳情，不淹沒主畫面。
- 不接受長時間等待後只有空泛的「審核失敗」，沒有可用結果或下一步。
- 斷線與執行失敗分開處理，能查回原 run，不為取回結果重做業務操作。
- 同一請求只能呈現一致的最新狀態，不同時顯示互相矛盾的完成／處理中訊息。
- 已保存的操作以原收據為準，不因文字生成失敗而假裝全部未執行。

### 4.3 固定官方求助入口

- 使用者希望檢查能獨立異步進行，並在固定位置顯示入口。
- 不依賴主 Agent 先決定調用工具才出現。
- 建議平時保持簡潔，命中相關情境再突出提醒；急迫情況不能完全藏在點擊後。
- 入口提示與正式答案審核是兩件事，不以入口檢查替代答案核對。
- 具體位置、常駐形式、判斷方式與緊急提示設計仍待定。

## 5. 建議技術方案（不是既定實作）

### 5.1 原文、索引與結構化資料分開

- RAG 是先檢索證據再生成，不等於所有資料必須向量化。
- 官方長文件：原文保存＋有版本的片段／語義索引。
- 精確產品型號、地區版本、批次、價格與事件狀態：按需取得並以結構化欄位核對，不只靠向量相似度。
- 如需樣本統計，先建立可追溯、去重的觀察，再由程式計算；不讓模型憑少量命中自行推算整體比例。
- 私人家庭資料與公共知識分隔，不進公共索引或跨家庭快取。
- 權限、預算及系統規則由程式／受控設定管理，不靠檢索命中才生效。

### 5.2 官方資料處理

取得原文 → 解析／必要時 OCR → 檢查完整性 → 按章節或完整主題切段 → 建立索引 → 校驗 → 發布。

- 保留頁碼／段落位置、來源 URL、版本、日期、地區與適用條件。
- 不把例外、年齡範圍、表格標題及單位切散；可從短片段讀回相鄰內容。
- 新版準備完成才切換檢索版本，避免未完成內容直接成為回答依據。
- 舊版退出當前檢索，但按需要保留追溯資料。

### 5.3 檢索與生成

- 口語需求用語義檢索；產品名、型號、批次及日期用精確欄位／關鍵字。
- 結合地區、年齡、有效期等條件；候選去重，必要時重排。
- 生成前先檢查證據是否足夠，明顯缺項先補查或補問，不等最後才發現沒來源。
- 可以先展示已找到的來源卡與原文入口，再交付核對後的整理答案；來源命中不等於個別建議已獲核實。

### 5.4 預算與審核恢復

- 主流程保留正式審核的模型次數與時間；修正＋重審也納入總預算。
- 收尾規劃須按當前交付路徑計入初次審核，以及仍允許的修訂／重審與終態交付，不只預留最後一次生成及終態工具。餘額不足時提早有界收束並說明缺項，不讓模型先耗盡再跳過審核；具體 reserve 算法及政策相容待實施驗證，現有缺口仍見第 10 節。
- 格式／引用錯誤回傳具體原因，限制同類無效提交，不只提高總次數。
- 證據不足時允許有界補查或必要澄清，不無限循環。
- 區分內容不受支持、證據不足、技術故障及預算不足，避免全部映射成同一個籠統訊息。
- 官方答案核對與原文是否一致；社群摘要核對是否忠實反映原帖；統計數字由程式驗算，不混用證據標準。
- 部分內容可交付時，其自身仍須符合校驗／核對要求，不能把未核草稿直接當正式答案。

### 5.5 成本與維護

- 文件未變不重做 embedding，只處理變更部分。
- 快取綁來源版本、有效期與適用條件；來源撤回或改版時失效。
- 公共檢索可適當復用，私人資料不可跨家庭共享。
- 生成、工具、檢索、審核、修復及重試分開觀測，同時受整體預算約束。
- 優先沿用現有 Firebase／Firestore 與儲存架構；全文搜索方案、版本能力與成本先驗證，不預設要搬資料庫或購買服務。

## 6. 實施階段與交付物（建議）

### 階段 0：現況盤點與範圍固定

- 核對最新程式、實際部署版本、已有來源、已完成與未驗收能力。
- 用原 run 的安全診斷資料追查失敗，不以截圖推論取代證據，不重跑同一問題消耗額度。
- 選定第一批代表性問題與官方文件。

交付物：差距清單、首批來源清單、驗收案例與工作包。

### 階段 1：官方搜索可用版

- 跑通官方原文解析、搜索、上下文讀取、引用答案及核對。
- 修復審核預算、反覆提交、斷線查回與狀態顯示問題。
- 先達成一條完整好用的流程，不先追求全量收錄。

交付物：可測試的官方搜索完整流程及對應測試證據。

### 階段 2：搜索前端本地預覽

- 整理提問、進度、來源、答案、補問、失敗及恢復狀態。
- 加入獨立異步的官方求助入口設計。
- 使用合成資料／模擬供應商，驗證 Web 及手機尺寸。
- 可與階段 1 並行，但模擬驗收不能冒充真模型品質驗收。

交付物：可互動本地預覽及狀態／畫面驗收紀錄。

### 階段 3：時效資訊庫

- 增量檢查、事件去重、更新、更正、解除及過期處理。
- 先做到可查詢近期事件，再接重要且相關的提醒。

交付物：事件查詢流程、更新任務、保留規則與通知設計；是否啟用真實通知另確認。

### 階段 4：按需社群與產品搜索

- 先選少量來源驗證搜索、原文可讀性及使用方式。
- 整理社群觀點、產品差異及來源，不建立長期論壇庫。
- 覆蓋讀不到原文、舊帖、矛盾說法、不同型號及疑似廣告等情境。

交付物：可追溯的即時搜索結果與定性整理流程。

### 階段 5：整體驗收、擴大覆蓋與後續助手

- 記錄完成率、來源／引用正確性、等待時間與成本，再擴充資料來源。
- 真模型端到端驗收需明確範圍與有界預算；不能只用 scripted provider 代表真模型效果。
- 發布依實際改動區分 Web、OTA 或 APK，並保留回退與版本證據。
- 搜索主流程穩定後，再規劃代辦、成長、文件與持續助手功能。

# REQ-002｜Agent 提速、可見進度與分階段交付

## 1. 需求意圖與目標

使用者希望同時改善三件事，而不是只把等待畫面做得更熱鬧：

- **A．讓必要流程少繞路：**減少不必要的模型往返、串行等待、重複搜索及無效修正，實際縮短完成時間。
- **B．持續顯示真實、有意義的過程：**讓使用者知道正在查甚麼、已找到甚麼、還差甚麼，以及是否受阻；不是假進度、內部思考逐字稿或一直轉圈。
- **C．分階段交付，而不是最後才全部出現：**在符合權限、來源及審核條件下，較早提供可用資料，再補齊答案與細節，不讓已可靠完成的部分陪最後一步一起等待。

三者分開量度：畫面較早有動靜不等於答案較早可用，首個可用結果較早也不代表總完成時間或品質已改善。不能以跳過必要求助提示、引用、審核、授權或保存來換速度。

**目前狀態：需求與建議實施計劃，尚未實作。**下列介面、並行方式、分段交付單位及效能門檻須在實施時核對，不因本文件列出便視為現有能力。

## 2. 與 REQ-001 及既有工程的關係

- REQ-001 決定搜索產品方向、三類來源及內容可信度；本包補充其執行效率、等待呈現及交付時機，不另造一套資料架構或重寫 REQ-001。
- 共用同一個原 run、來源／引用、權限、預算、審核、結果保存及恢復契約；正式實施時把重疊工作合併到同一責任包，避免兩邊各改一套。
- REQ-001 已指出審核預算與失敗恢復缺口；本包的批次搜索、修正及分段審核須一併計入原 run 總額，不能先花光再期待審核免費執行。
- 既有 PLAN 的正文串流工作與本包可能重疊，實施前須對齊範圍及披露規則；本次需求文件不直接修改既有權威計劃，也不授權先把未核對的照護結論逐字展示。

## 3. A：讓必要流程少繞路

### 3.1 一輪規劃多個獨立查詢，有界並行

若同一問題需要互不依賴的 `xxx`、`aaa`、`bbb` 三項資料，模型應可在同一輪提出三個查詢，而不是「問模型 → 查一項 → 再問模型 → 再查一項」逐項往返。

- 優先沿用現有多工具呼叫能力。已核 ADK JS 2.1.0 對同一回應的多個 function calls 採逐項 `await`，同輪多查詢可減少模型往返，但不等於工具已同時執行；固定來源見第 9.1 節。實施時再核選定版本、模型能否產生合適的一組呼叫，以及項目的有界並行接點，不把靜態原碼當實際提速證據。
- 只對已確認互不依賴、唯讀且獲授權的查詢並行；需要先得知型號、年齡、地區、來源內容或前一項結果的後續查詢，仍按依賴次序執行。
- 設置可配置的批次大小、同時在途數、每項逾時與整體期限；具體值先測量再定，不預設無限並行，也不把全部查詢塞進一批。
- 每項查詢保留獨立身份、來源、成功／失敗狀態及工具／供應商用量。一次批次呼叫不能把多項成本隱藏成一次，並行前仍須通過可用預算與配額檢查。
- 一項失敗不丟棄其餘已成功資料；只在有價值、有餘額且可安全重試時補該項。逾時、取消、撤權及原 run 終止後，不讓排隊工作繼續偷偷執行。
- 保留終態工具邊界：`present_answer` 不與其他工具混在同一批，不能為減少一輪而提早宣稱完成。
- 只有原生多工具方案經最小驗證仍有明確缺口，才考慮小型 `batch_search` 封裝；封裝仍逐項授權、計量及回報，不更換整套 Agent 框架或另建通用排程平台。

### 3.2 工具一次回傳足以判斷的相關資料

- 搜索結果在輸出上限內提供相關原文片段、來源連結、日期／版本、適用條件及必要相鄰上下文，不只回一串 ID，再逼模型逐項追讀。
- 先讓模型判斷哪些結果有用，再按需讀全文；不得以「減少呼叫」為由塞入整份長文件、忽略輸出限制，或把搜索摘要當成已讀原文。
- 明示片段是否截斷、是否仍須補讀，以及可取回原文的位置；例外、表格單位、年齡／地區限制不能因壓縮而丟失。

### 3.3 清晰搜索問題走較短路徑

- 意圖已清楚的搜索問題直接進入必要檢索與回答，不每次重跑獨立路由、分類、能力介紹或多次模型載入。
- 只有實際缺少會改變搜索或答案的條件才澄清；不要為普通查詢先繞到代辦、成長記錄、記憶寫入等助手流程。
- 短路徑仍保留必要身份、權限、風險、來源及交付檢查；不是全局取消分類或繞過安全判斷。
- **沒有其他操作語義的單純「hi／你好／謝謝」直接作適當簡短回覆**，不無故載入全部模組、搜索、補讀 history 或啟動助手流程，也不另叫模型作意圖／路由分類。若同句另有實際請求，按該請求處理，不把關鍵詞當成跳過工作的規則；soft 預算不是要花到的支出目標。
- 核心 tool schema 在請求中存在，不等於工具已執行或所有能力已載入；`present_answer` 等必要終端交付仍可使用。這項要求不承諾零工具或固定只一個模型請求，亦不降低當次必要的內容審核、身份、權限及交付安全。

### 3.4 復用已取得的有效證據

- 同一 run 已成功讀到的資料不反覆搜索；使用者追問同一主題時，可在適用條件仍成立下沿用來源及必要上下文。
- 復用前核對權限、家庭／孩子範圍、來源版本、有效期、使用者新條件及資料是否更正／撤回；需要即時資訊時補查，不以快取代替時效核對。
- 公共資料快取與私人家庭內容分隔；不得跨家庭共用私人結果。摘要不是新的原文證據，來源失效或權限撤回後不能繼續引用。
- 復用讀取結果不代表重播操作；已保存的業務結果仍按原收據及原 opId 查回。

### 3.5 精準修正，不讓整條流程重來

- 格式、必要欄位及引用結構的拒絕回傳具體錯誤與可修正位置；能由程式確定修復的格式問題，優先局部處理，不另花一輪讓模型猜原因。
- 保留成功的檢索、工具結果及收據，只補缺項；不能為通過檢查刪掉必要引用、降低證據要求或改標內容類型。
- 修正正文含義、適用條件、證據或對象後，重新核對受影響的審核；舊審核不能套到新內容。引用格式修正也須重新執行相關校驗。
- 設定同類拒絕、補查、修正及重審的有界次數與停止條件，預留正式審核資源；相同失敗不能無變更重送到耗盡額度。

### 3.6 把可預先完成的工作移出互動等待

- 官方資料的解析、切段、索引及 embedding 在收錄或來源變更時處理；正常問答查已可用版本，不每題重新解析或計算整份文件。
- 沿用 REQ-001 的增量更新、版本切換與失效規則；新版本未完成驗證前，不混入正式回答。
- 主結果已可靠保存後，只有不影響當次答案正確性與可恢復性的非關鍵分析、統計或摘要，才考慮背景執行；需要後續使用的摘要在未完成前須有正確的回讀方式。
- 必要審核、授權／同意、關鍵寫入及其結果確認不能移到「成功」提示之後。背景工作另有可追蹤身份、失敗／恢復及預算，不以背景化規避原成本或授權限制。

### 3.7 先給足夠而精簡的答案，調校以證據為先

- 第一份答案先覆蓋直接問題、必要條件、來源及可行下一步，詳情可按需展開；不是刪去安全條件來縮短文字。
- 短答案與長文格式按問題需要選擇，不每題先產生完整長報告再縮寫一遍。
- 模型、供應商、思考設定及基礎設施的調校，排在實際瓶頸量測之後；比較品質、引用、完成率、成本與延遲，不單憑「較小模型較快」作決定。
- 不擅自換用未批准的模型／付款身份、增加配額、升級付費資源或犧牲原有品質門檻。

### 3.8 無工具角色的原生結構化輸出

- 編製、獨立審核及背景整理／核對等無工具生成，優先評估沿現有 gateway 傳遞 provider 原生 JSON schema 約束；採 ADK `LlmAgent` 時使用其 `outputSchema` 接點，直接 `completeText` 路徑則需明確接入相容的 `responseSchema`／JSON MIME 設定。把 schema 寫進提示詞不等於 provider 已啟用約束，不為此把現有角色一律改成 `AgentTool`。
- 先核指定模型、provider／SDK 的 schema 子集及無工具條件；支援時使用原生約束，不支援時明示降級為既有提示詞＋嚴格解析／有界修正，或返回清楚的不支援結果。不得靜默刪必要欄位、換模型／付款身份，或另開不計帳的修復生成。
- **格式合規不等於內容正確。**保留 Zod／業務校驗、來源及引用、內容／版本 hash、身份與授權、獨立語義審核及保存前重核；JSON 合法但證據不符、過期版本或撤權仍須拒絕。此為待實施方案，現況與官方接點見第 9.1 節。

## 4. B：持續顯示真實、有意義的過程

### 4.1 以真實事件產生進度

- 進度由實際請求、查詢開始／完成、來源取得、補查、審核、保存及受阻事件驅動，不靠定時器輪播「正在深入分析」或虛構百分比。
- 用家長看得懂的短句表達目前動作、已得到的結果及下一個必要步驟，例如「已找到兩份官方資料，正在核對適用年齡」；數量與動作必須有實際事件支持。
- 查詢尚未開始、來源只命中但未讀取、審核尚未完成時，分別如實顯示，不能提前聲稱已讀、已驗證或已完成。
- 連線 heartbeat 只代表連線維持，不是新工作進展；沒有新事件時保持最後可信狀態，必要時明示仍在等待，不製造假更新。

### 4.2 主畫面簡潔，細節可展開

- 主畫面保留目前階段、重要發現、明確阻塞及可行操作；工具名稱、次數、耗時與安全診斷放入可展開詳情，不要求家長理解技術流水帳。
- 不展示模型內部思考逐字稿、隱藏提示詞、私人正文或原始工具參數；進度說明不冒充模型完整推理。
- 若供應商原生提供可對外展示的推理摘要，可另行評估其內容、標示及實際效益；清楚區分「模型摘要」與程式確認的執行事實，不為播報過程額外呼叫一個模型。
- 讀屏可理解主要狀態，更新不搶焦點或連續刷屏；Web 與手機使用相同狀態含義，不用不同端的動畫推測工作是否完成。

### 4.3 進度與原 run 的權威狀態一致

- 事件綁定原 run 及可去重／排序的識別；並行查詢可以完成次序不同，但不得重算同一項、倒退到過時階段或顯示錯誤的來源數。
- 斷線重連先查回原 run、已保存結果與最新權威狀態，不為恢復畫面重跑搜索、生成或業務操作。
- 完成、部分可用、失敗、取消、逾時及結果尚未確認要可區分；已完成後不再留下「原運行仍在處理」的過時警告。
- 連線斷開不等於 Server 已失敗或已取消；對取消及未知結果的說明以 Server 確認為準，恢復後收斂到同一終態。

### 4.4 角色級 metadata-only 追蹤與事件接點

- 沿現有 runtime／gateway、編製／審核入口及背景工作台帳，關聯原 root／工作、角色、階段、模型 attempt／工具子項的安全識別；記開始／結束、耗時、狀態、受控失敗細碼、模型輪次／工具量、可取得的 tokens 及審核／收尾剩額。直接走 `completeText` 的角色亦須涵蓋，不能只追主 `LlmAgent` callbacks 便宣稱四角色可觀測；不得為追蹤新增模型呼叫。
- 復用第 7.1 節時間點，分開來源首次可展示、答案首次獲核准及整輪終態；失敗帶實際角色／階段，未知就標未知。從同一事實事件映射既有 SSE 的來源取得、角色處理、審核與保存進度，詳情不暴露內部正文；不另建第二套權威狀態，也不把 token 到達當正文已可披露。
- 項目已關閉 ADK span 正文捕捉並停用其 logger，須保留此邊界；不能把上游預設當安全預設。若接入 OpenTelemetry／exporter，採最小 metadata 欄位白名單、最小保留及存取範圍，預設不收家庭正文、prompt、模型回答、工具參數／結果、完整私人查詢、附件或憑證；例外／錯誤及重試路徑亦不得繞過，不能只靠 UI 隱藏或事後遮罩。
- 用合成識別字串核對 span attributes／events、logger 及實際 exporter payload 的允許欄位與禁收內容；核對四角色、直接 gateway 呼叫及失敗／取消仍可對回原 run，沒有因脫敏而遺失必要計量或把臨時聊天正文持久化。現有保護不等於新增全路徑追蹤已驗，固定證據見第 9.1 節。

## 5. C：分階段交付，而不是最後才全部出現

### 5.1 建議的三層交付

1. **來源／資料層：**權限及展示檢查通過後，先顯示已取得的來源卡、標題、可確認日期與有界原文片段。清楚標示「已找到／已讀取」，不等同「此來源適用於你的孩子」或正式建議已獲核實。
2. **可獨立成立的答案部分：**只有自身證據、適用條件及必要校驗／獨立審核都通過的部分，才作正式答案交付；可能影響結論的上下文不能拆到稍後才補。
3. **補充與詳情：**再加入其餘已通過的比較、解釋及來源細節；說明仍待處理甚麼、已完成甚麼，不讓使用者誤以為第一段就是完整結論。

這是待驗證的交付設計，不是把整篇草稿切成幾段便可繞過目前整體審核。若無法安全分出獨立部分，先提供來源層與真進度，待完整答案通過後才交付。

### 5.2 分段交付的安全與一致性

- 不先串流未核對的照護／醫療結論，再希望以撤回補救；不能把年齡、例外、禁忌、急迫求助條件放在使用者尚未看見的後半段。
- 分段審核須明確綁定內容、來源、對象及版本，且保留跨段一致性核對；內容變更使既有核准失效時，按影響範圍重新審核，不默默沿用舊結果。
- 先以少量代表情境驗證分段是否真的較早產生可用內容、是否增加模型次數與總延遲，以及是否降低品質；未有實益就不增加複雜度。
- 開啟模型串流不會自動解決工具參數、引用、審核、保存及跨端狀態問題；逐字輸出與可安全交付是不同能力。
- 已完整緩衝的核准答案直接顯示，不再故意延遲逐字打字；真串流也不能把內部思考或尚未通過披露條件的正文送出。

### 5.3 後段失敗時保留已可靠取得的成果

- 最後整理或補充失敗時，保留仍獲授權、來源有效且自身已達展示／交付條件的來源卡及已核准部分，不把整頁清空成一句錯誤。
- 明示這是部分結果、缺少哪一部分、為何未完成，以及可用的查原 run、補問或有界重試入口；不把部分可用標成整項完成。
- 未核准草稿不因最後失敗而升格為正式答案。撤權、來源失效或內容被證明錯誤時，以安全及有效性為先，不能為「保留成果」繼續展示。
- 已有業務操作仍以原收據為準；回答失敗不回滾成「甚麼都沒做」，也不自動再次執行。

## 7. 指標與建議驗收清單

### 7.1 指標定義

- **首次有意義進度時間：**請求獲接受至首個可讓使用者理解實際工作的事件；不把純 spinner、已收到或 heartbeat 當成改善成果。
- **首次可用結果時間：**請求獲接受至首個達展示條件的來源／資料或核准答案部分；來源卡與正式答案分開統計，不混成「答案已完成」。
- **總完成時間：**請求獲接受至權威終態及結果可恢復；成功、部分結果、失敗／取消分開分析，不能以提早失敗充當提速。
- 在同類問題、相近來源／模型／預算及清楚冷／熱快取條件下比較；樣本足夠後才報 p50／p95，樣本不足明示，先不承諾固定秒數、百分比或零失敗。
- 同時觀察完成率、來源／引用正確性、適用條件與答案品質、模型輪次、逐項工具量、重試／審核量及每個完成請求成本；速度變快但護欄退步不算通過。

### 7.2 驗收場景

| 場景 | 應驗證的結果 |
|---|---|
| 單純 hi／謝謝且沒有其他操作語義 | 直接簡短回覆，不無故全載模組、search／history／助手流程或多叫分類模型，不為用滿 soft 做工作；必要審核／終端交付保留，schema 存在不被錯算成工具執行 |
| 三項已知互不依賴的搜索 | 相對逐項往返基線減少模型輪次；有界執行、逐項計量，結果仍完整可追溯 |
| 後一查詢依賴前一項型號／內容 | 等前置完成再查，不為並行提前猜條件或查錯對象 |
| 批次超限、一項逾時或失敗 | 不超並行／配額／整體期限；保留成功項，只對必要失敗項有界處理 |
| 查詢中取消或撤權 | 排隊／在途結果按既有安全契約處理，不再披露失去權限的資料，不把未確認取消當已停止 |
| 搜索結果需補原文 | 回傳相關片段及完整來源條件；缺漏／截斷明示，不以摘要冒充原文 |
| 追問復用與來源更新 | 有效資料可復用；版本、有效期、地區／年齡或權限變更會重新核對／失效，私人資料不跨家庭 |
| 格式／引用拒絕 | 精準補錯、保留成功資料、有界次數及正式審核資源，不反覆原樣提交 |
| 無工具角色的原生 schema 與降級 | 模擬 provider 可觀察到正確 schema／JSON 設定；不支援路徑明示且仍嚴格校驗。合法 JSON 但錯引用／hash／版本／授權不能通過；拒絕及修正仍計原帳 |
| 修正影響正文含義或證據 | 受影響內容重新審核，不套用舊核准或移除必要引用求過關 |
| 接近收尾餘額及修訂／重審 | 規劃保留該路徑必要 review／revision／re-review 及交付資源；不足時如實收束，不把只剩最後生成的 snapshot 當審核已獲保證 |
| 並行事件亂序／重複 | 以實際事件去重及收斂，來源數、工具數、當前階段與終態不矛盾 |
| 斷線後原 run 完成 | 查回原結果與終態，消除過時 running 提示，不另開 run 或重做業務操作 |
| 來源先到、答案仍審核中 | 來源卡不冒充已核准建議；必要適用條件及求助訊息不被延後隱藏 |
| 分段答案涉及照護結論 | 未核准正文不先披露；已交付部分可獨立理解，條件完整且跨段一致 |
| 最後補充失敗 | 合格的部分成果保留，缺項與下一步清楚；未核草稿不升格為正式答案 |
| 非關鍵工作改為背景 | 主結果先可靠保存；背景失敗可追蹤／恢復且有獨立預算，不延後關鍵審核或寫入 |
| Web／手機／輔助閱讀 | 主要進度、部分可用、核准、失敗及恢復含義一致；詳情可操作，更新不搶焦點 |
| 四角色追蹤與 OTel 禁收正文 | 正常、失敗、重試與取消可用 metadata 關聯原 run／角色／階段及首結果時間；合成敏感標記不進 span／log／exporter，直接 `completeText` 路徑不漏計或重複計量 |

## 8. 待決事項與本包不展開的工作

待決事項：
1. 代表問題、基線環境、樣本量、時間點定義及品質／成本可接受門檻。
2. 已知 ADK JS 2.1.0 多工具逐項執行；實施時核對選定版本及模型採用情況，再決定最小有界並行接點或 `batch_search`，不把同輪呼叫誤當並行已落地。
3. 並行上限、批次大小、每項逾時、取消／部分失敗策略，以及審核預留如何配置。
4. 工具結果片段／上下文上限、追問復用範圍、快取有效期與版本失效條件。
5. 進度事件契約、詳情層級，以及是否採用供應商原生可公開的推理摘要。
6. 哪些來源卡／答案部分能獨立交付、分段審核與最終一致性核對的單位、額外成本與停止條件。
7. 與 REQ-001、既有審核及串流工作包的共同責任、接口與實施次序；真模型驗收的有效批准與預算。
8. 無工具角色的 schema 相容／降級契約、角色事件與 trace 欄位白名單／保留及 exporter 邊界；同 run compaction 的接入與驗收沿 REQ-005 第 4.2 節，不重建跨聊天記憶。

本包不直接展開：更換整套 Agent 框架、通用多代理／排程平台、全量性能或壓力測試、未批准的模型／付費資源切換、繞過引用或審核、展示內部思考、真實家庭資料外發，以及尚未要求實施的其他助手功能。

# REQ-003｜助手操作授權、主聊天模式與臨時聊天

## 1. 需求意圖與範圍

讓使用者自行決定「只是問一問」還是「請助手正式記下／修改」，避免普通聊天被不必要的助手流程打斷；需要自動處理時，則在清楚授權內直接完成，讓使用者看結果。

本包包含四項相連需求：助手操作預設先確認、沿用「記錄與核對」的待確認卡片、同一主聊天的「只是聊天」模式，以及完全獨立且退出即清除的臨時聊天。

**目前狀態：需求及建議實施計劃，尚未啟動本需求包工程。**沿用現有頁面與業務能力，不把它們全部視為缺失；操作歷史、撤銷、草稿及確認綁定的實際覆蓋須先盤點。下列模式／授權／清理契約是待落實方案，不代表已通過驗收。

## 2. 助手操作：預設先確認，可選授權內自動保存

### 2.1 預設行為

- 助手可先整理擬新增或修改的內容，形成待確認草稿；使用者確認前，不提交成正式記錄或其他正式業務變更。
- 草稿與正式保存明確區分，不能一邊說「等你確認」，一邊已改動正式資料；草稿本身的暫存沿既有待確認機制處理，不冒充正式成果。
- 使用者能看懂將改哪一項、目前內容與建議內容有甚麼差異，再選擇確認、修改或取消。
- 「取消」是放棄該項未執行草稿，不等於撤銷已保存的歷史操作；兩種狀態及後續動作不能混用。

### 2.2 可選的自動模式

- 使用者主動選擇自動模式後，助手可對**當前授權範圍內**的操作直接正式保存，再展示實際結果與可查核的收據／狀態，不必每次重複確認。
- 新增與修改可作少量、容易理解的細調；具體分組先依現有可執行能力整理，不建立大量難懂的分類、每個欄位一個開關或泛用權限設計器。
- 沒有授權、超出範圍、授權已撤回或目標不明時，不自動執行；依情況保留草稿請使用者確認，或說明不能執行及缺少甚麼。
- 自動模式不是擴權：不能據此取得其他家庭／孩子資料、執行未有的功能，或跳過該動作原本需要的額外批准。本包不新增項目範圍以外功能或未有功能的授權選項。
- 自動操作的授權設定及流程只適用於助手模式；「只是聊天」與臨時聊天不需要選擇自動授權，不展示或啟用相應的自動操作設定 UI。這不免除服務本身必要的登入、存取與用量檢查。

### 2.3 內容審核與動作授權分開

- 內容是否有根據、格式／引用是否正確、是否通過必要審核，是內容交付條件；是否准許寫入或修改某項資料，是動作授權條件。
- 內容審核通過不等於使用者已確認寫入；選了自動模式也不代表可以保存未通過必要檢查的內容。正式保存須同時符合相關內容要求及當前有效授權。
- 建議把確認綁定到具體目標、擬執行動作、草稿版本及必要的原資料版本；使用者修改草稿或資料已被其他操作更新後，不能沿用舊卡片的確認去保存另一份內容。
- 授權變更、模式切換、重複點擊或回應遺失時，核對當前有效條件及原操作結果；不以重送新操作來猜是否已保存，也不默默重做先前已完成的操作。

## 3. 沿用「記錄與核對」，右上角只作快捷入口

- 使用者指定沿用既有「記錄與核對」頁面處理待確認卡片與操作歷史；不另建第二個待確認匣、第二套歷史或不同的狀態權威。
- 右上角入口只是較方便地查看**同一批未確認卡片**，不是新增一個業務資源；其數量、卡片內容及狀態與「記錄與核對」一致。
- 兩個位置都能看到可讀的變更差異，並使用同一項確認／修改／取消操作。從任何一處修改或處理後，另一處同步更新，不保留仍可重複提交的舊卡片。
- 卡片應區分草稿、待確認、處理中、已保存、已取消及結果尚未確認等必要狀態；實際名稱及覆蓋沿既有契約核對，不為本包另造複雜狀態分類。
- 修改草稿後顯示最新差異；重複確認或多端同時處理時，以同一卡片、版本及原操作結果收斂，避免重複新增／覆蓋。
- 已保存的操作沿用現有歷史入口；**先核對哪些動作確有撤銷實作、限制及證據，再決定可顯示的撤銷操作。**不宣稱所有操作都可撤銷，也不把歷史頁存在當成撤銷已驗證。
- 本包以現有記錄、修改及確認能力為界；若盤點發現個別撤銷缺口，另列範圍、風險與必要決策，不順帶建立全站通用回滾系統。

## 4. 單一主聊天：助手與「只是聊天」可切換

### 4.1 保留同一段對話與產生模式

- 「助手」與「只是聊天」共用同一主聊天，不另開一份聊天或清走先前對話；切換後 Agent 仍知道原有上下文。
- 上下文要保留內容產生時的模式，讓 Agent 分清哪些是聊天討論、哪些是已提出的草稿、哪些是有收據的正式操作；不能在切回助手時把歷史聊天重新標成待執行指令。
- 模式切換本身不構成新的保存、確認、取消或補做授權。此前的草稿仍按原狀態管理，已完成操作也不能因切換而重做。
- 同一主聊天為承接對話所需的**技術摘要**，與正式事實、長期私人記憶／偏好及助手任務分開。只是聊天的內容可按需納入承接摘要，但須保留來源訊息 ID／版本及產生模式，不因此變成已確認事實、持續指令或操作授權；切回助手不補存、不重播。
- 摘要沿既有按需／背景及正確覆蓋機制處理，不為每輪 hi／謝謝強制生成摘要，也不額外加入互動意圖分類模型。主聊天的承接摘要仍受其資料保護與來源有效性約束；臨時聊天不得被吸收到主摘要／長期記憶，退出清除沿本包原規則。

### 4.2 使用者手動選「只是聊天」

- 使用者手動切換後，按明確模式調整模型提示詞，告知現在不需要助手功能，停止相應助手流程與工具，保留搜索及問答。
- 不額外呼叫模型來分類「這句是否其實想生成文件／記錄」，不再多跑意圖路由、助手規劃或自動授權問卷；模式由使用者已作出的選擇決定。
- 建議同步限制本次可用工具及由 Server 檢查寫入動作，避免只靠一句提示詞保證不操作；這是程式／工具能力邊界，不是額外 LLM 判斷流程。
- 可在聊天內討論、比較、解釋或產生純文字內容；這些回覆仍是聊天產物，不因此建立正式文件、記錄、待辦或待確認卡片，也不自動啟動助手式記憶寫入。
- 「只是聊天」**不是臨時聊天**：既有主聊天上下文照常保留，可供後續追問及切回助手後理解；不能套用臨時聊天的清除規則。

### 4.3 切回助手後可引用，不自動補做

- 切回助手後，Agent 可以理解之前只是聊天模式的內容，但在使用者沒有提及時，不自動把之前的建議、文字或討論重新生成正式資料、補做任務或重播操作。
- 使用者可直接說「把剛才那份記下來」，引用原聊天內容，不需要完整重述；依原內容與指涉判斷目標，有實質歧義才作必要澄清。
- 這項明確新請求在助手模式按當前設定執行：預設形成待確認草稿；自動模式且在有效授權內則可直接保存。先前聊天內容本身不是保存授權。
- 若使用者仍在「只是聊天」提出保存要求，不在背景偷偷改成助手；提供清楚的切換／確認入口，待其明確選擇後才進入助手操作，不以額外模型意圖分類來決定是否偷偷開流程。
- 切換時若有執行中的助手工作，要區分未發出的寫入與已發出／已完成的操作：未執行的寫入不得在只聊界面悄悄啟動；已發出的操作查原結果，不能假稱已撤回或重送。具體中止與提示規則在盤點後固定並驗收。

## 5. 左上角臨時聊天：獨立空白、退出立即清除

### 5.1 獨立範圍，不借用主聊天上下文

- 從左上角進入獨立空白臨時聊天，不載入私人記憶、孩子資料、主聊天歷史或任務，也不因當前主界面選了某個孩子就自動帶入其資料。
- 只使用公共資料庫與搜索能力；臨時會話內可沿用**當次臨時聊天**的訊息追問，但不讀其他會話的私人內容。
- 使用者在臨時聊天自行輸入的內容只用於當次回答／追問，不因此建立私人記憶、孩子記錄或主聊天摘要。臨時聊天不需要自動操作授權 UI 或助手保存流程。
- 必要的身份、權限與用量控制留在服務控制層，不把私人資料或主聊天上下文載入模型來完成這些檢查；「臨時」不等於免費、匿名或不受服務限制。
- 建議在請求組裝、可用工具及 Server 存取範圍同時隔離，避免只改前端畫面或提示詞、後端仍讀取主聊天資料。實際 scope／session 形式沿現有架構選最小改動。

### 5.2 不回寫主聊天、記憶或任務

- 臨時聊天的問題、答案、摘要、搜索結果及待處理工作，不回寫主聊天、私人記憶、任務或「記錄與核對」卡片，也不被主聊天背景整理流程吸收。
- 不把臨時私人正文、來源查詢全文或模型上下文寫入一般持久日誌、診斷 trace、分析事件或持久快取。只保留必要且不含正文的安全／用量事件時，另列最小欄位與保留範圍。
- 搜索所得公共文件本身與臨時對話／個人化查詢資料分開處理；退出不要求刪掉全站原有公共知識庫，也不能以公共快取名義保存臨時私人上下文。

### 5.3 正常退出即清除，晚到結果不能復活

- 使用者正常退出時，前端立即清除該臨時聊天的顯示、訊息及上下文，並立即通知 Server 清除該臨時會話在項目控制範圍內的內容、上下文與暫存，同時使該會話失效；重新進入必須是新的空白會話。只標記失效但仍保留內容，不算完成清除。
- 退出要同時阻止該會話再接收或保存結果；取消可取消的臨時請求，已發出但不能即時取消的供應商呼叫即使稍後回來，也不能重新顯示、回寫主聊天或恢復已清除的臨時上下文。
- 建議使用會話範圍及失效標記／版本阻擋晚到結果，並限制清理只影響該臨時會話；不能誤清主聊天、未確認卡片或原有任務，也不能取消無關主聊天工作。
- 清除涵蓋前後端實際使用的臨時容器及上下文副本，需盤點模型 session／事件儲存、快取與診斷路徑；只清空畫面不算完成。具體儲存方式及清除證據留待實施時確認。

### 5.4 異常退出與控制範圍須如實說明

- 關閉分頁／App、崩潰、斷網或裝置失聯時，Server 不一定即時收到退出事件；不能聲稱離線一刻已保證遠端全部刪除。
- 需設計失聯清理與最長存留期限，例如有界存活／續期及逾期清理，並驗證恢復連線後不能續接已失效會話；具體機制、時限與提示仍待確認，不以無限期保留作預設恢復方案。
- 若前端已清除但 Server 清除尚未確認，須區分本機已清除與遠端待確認，不顯示無證據的「全部已清除」；仍須主動收斂失效與清理，不能因一次通知失敗便永久保留。
- 項目只承諾其能控制的應用端內容與上下文處理；第三方模型／搜索供應商的日誌及保留政策須按實際接入確認，不能無依據承諾已同步刪除第三方副本。
- 本包不授權更改第三方帳戶、服務保留政策或新增付費隱私方案；若現有供應商限制影響需求，先明示差距，再由使用者決定。

## 6. 與其他需求包的關係及建議實施次序

- 與 REQ-001 相容：助手、只是聊天及臨時聊天均可按各自資料範圍使用搜索問答；臨時聊天只用公共來源，不能為個人化搜索私下讀取家庭資料。
- 與 REQ-002 相容：手動模式直接決定提示詞與能力範圍，不新增意圖分類模型輪次；正式寫入的版本、收據、真進度及原 run 恢復仍共用既有規則，不因自動模式跳過審核或假報成功。
- 本文件只增補需求，不直接更改 SPEC／PLAN 的權威契約；開始實施時先對齊現有確認、授權與資料隔離定義，遇到衝突列清後裁決，不另外平行建立一套。

| 只是聊天／臨時聊天的 UI | 不要求設定自動操作授權；必要登入、權限與用量檢查仍有效 |

| 臨時聊天內容與日誌檢查 | 不回寫主聊天、記憶、任務或卡片；一般持久日誌／trace 不留臨時正文與上下文 |
| 正常退出臨時聊天後重新進入 | 前後端該會話內容及上下文按契約清除，舊會話失效，新會話空白；不是只清畫面或只改失效標記 |
| 退出後舊搜索／模型結果才返回 | 不重建已退出會話、不寫回任何主資料；主聊天、既有卡片及任務不受影響 |
| 關閉、斷網、崩潰或失聯 | 本機清除與遠端確認分開；按已定時限清理孤立會話，不誤稱 Server 即時收到事件，也不無限保留 |
| 既有流程回歸 | 既有搜索、正式助手操作、待確認處理及原操作恢復仍有效；臨時清理不刪主歷史，主聊天切換不套用臨時清理 |

## 8. 待決事項與不做事項

待決事項：
1. 既有「記錄與核對」卡片、確認綁定、操作歷史及各項撤銷的實際實作／驗證範圍。
2. 自動模式可涵蓋的現有新增／修改動作、少量細調方式、授權保存／撤回及生效時點；不添加未有功能的授權選項。
3. 模式切換、草稿變更、在途操作與原操作查回的具體契約；只聊期間既有草稿保持原狀態，不能因切換而默認確認或取消。
4. 產生模式如何帶入主聊天上下文、前文引用如何綁定來源，以及只是聊天時需要保留的最小搜索能力。
5. 臨時 session／scope、上下文／事件儲存、快取與日誌實際落點，正常退出的清除證據與晚到結果阻擋方式。
6. 異常退出的最長清理時限、失聯偵測／失效機制、遠端清理未確認時的提示，以及第三方供應商可控制與不可保證的保留範圍。
7. 最少合成驗收情境及與 REQ-001／002、現有模式／授權契約的實施歸屬。

不在本包直接展開：新的待確認匣或平行歷史頁、全站通用撤銷引擎、項目範圍以外的新功能、額外 LLM 意圖分類、將只是聊天改成自動清除、把臨時聊天變成助手保存模式、未批准的供應商保留政策／帳戶變更，以及正式部署或真模型測試。

### 3.1 以來源清單、快照與處理狀態持續同步

- 設計意圖是「每次只做仍有必要的工作，同時不漏掉新文件或舊欠項」；**程式 → 低成本模型 → 正式 Agent 的按需升級，與復用上次成果，是同一工作流的兩個維度，不是僵硬互斥的 A／B 路線。**已能確定需要語義整理時可直接進正式 Agent，不先付一次便宜模型費用作形式分類。
- 每個已登記來源保留來源清單、發現位置、已知文件穩定身份與範圍、原文快照／hash、讀取方法及政策版本、每步成果與缺漏。**發現新文件**沿可用目錄、列表、feed 或其他已許入口巡查；**同步既有文件**則核對已知文件是否改版、撤回或失效。只反覆讀已知 URL 會漏新增，只看最新清單亦不能保證舊文件未修改。
- `observed`（已觀察原文）、`processed`（已完成必要解析／整理／核對）與 `published`（已正式發布）分開記錄版本與狀態；下載成功不能推進全部三者。新觀察版本與舊發布版本可同時存在，未完成批次、缺少索引及發布欠項不能因下一次 hash 相同就消失。
- **無變更、相同方法／政策仍有效且沒有待處理欠項的檢查，模型呼叫為零**；仍可有程式讀取、比對與必要抽驗成本。未變但未處理／未核對的內容，或已變更方法／政策需補驗的範圍，沿原工作補缺；不能把「無新內容」解讀為禁止完成舊欠項，也不能藉接續重跑成功成果。
- `ETag`、`Last-Modified`、RSS／Atom、sitemap、列表日期等是可用線索，不是所有網站都提供、可靠或完整的統一真相。結合內容 hash／已驗正規化差異與來源覆蓋核對，按可調政策定期讀回內容及較低頻全面覆核**已登記範圍**；不以單一首頁、feed 或 sitemap 保證全站沒有漏更新。

### 3.2 可重用的讀取方法與差異分流

- 初次接入先沿既有通用 parser 及格式能力探索已許範圍，辨識發現入口、文件擷取／分頁、正文與結構化欄位、原文定位及差異判斷方法；有缺口才提出來源專用設定，不先替每站寫一套程式。來源模組是**可替換、版本化的宣告式讀取設定及其依賴**，不是建立後永遠不用再讀網站的魔法。
- 已驗證的設定連同適用網站／格式／範圍、驗證時間、代表樣本、預期欄位／完整性測試與已知限制保存，後續直接重用。設定只可使用系統支援且受限制的能力，不能把網頁或匯入包提供的程式／提示當可執行權限；可攜邊界見 REQ-006。

| 本次證據與差異 | 最少必要處理 | 必須保留的門檻 |
|---|---|---|

- 共用 `0.25` 預設可按角色／工作類型在同一中央政策中覆蓋；顯示最後採用的比例、來源、版本及 soft／hard 有效值，不另散寫常數。管理員調平台／公共政策，本人調其 key 的個人消耗政策；**後續改比例透過既有設定入口生效，毋須改程式碼或重新部署**，仍受權限、政策版本及共享安全／供應商限制約束。角色覆蓋不另發一份 root 額度。
- soft 是正常規劃目標，**不是停止線、額外配額或強迫用滿的目標**。必要流程超過 soft、仍有進展且 hard 及其他有效邊界容許時，可沿原工作繼續；不得為守住 soft 而跳過審核、縮掉必要品質或過早宣告失敗。hard 保持最後保險；模型不能自行提高比例／hard、換付款身份或另開 run 清零。
- 程式以既有計量／事件提供已用量、soft 目標、hard 剩額及審核／收尾預留，供正常規劃與後續模型回合使用；**不為每一步審額另加模型呼叫或預算分類流程**。越過 soft 只作規劃／觀測訊號，是否需要調整依真實進度與餘額判斷；必要審核及收尾仍有可見預留，不能把 soft 當硬牆或用完才補計量。

### 3.2 在途政策變更的契約仍待明定

調高／降低 hard、改 soft 比例、撤權及重啟接續時，需驗證在途與後續派發如何依明定契約使用政策版本；有效值、版本及來源可見，原 root／工作總帳不清零，不能另領額度。**本文件不預先決定即時套新值或沿舊快照的生效規則**；實施前固定相容與狀態處理，撤權仍遵守既有安全約束。已發出 provider 請求未必可取消，須區分未發出、在途、已完成與取消未確認，不能假稱政策改動就已停止供應商工作。

### 4.2 同一 run 的原生 context compaction 與跨聊天記憶分層

- 第 4.1 節處理既有 recent／history／聊天摘要的選取、覆蓋及前進性；本節另評估長 run 內持續累積的工具／模型 events。項目目前以 [`runId` 作 `sessionId`](https://github.com/2NTTY/child-ai-caregiver/blob/19ac8dec3f6364241f29814c24b602305bdffad3/server/agent-runtime.ts#L493-L505)，故此處的「同 run」是本項目接入範圍，不是聲稱 ADK 原生只能處理單次 invocation。`TokenBasedContextCompactor`＋`LlmSummarizer` 是候選接點，未接入，也不取代 Firestore 的跨訊息／聊天歷史、私人記憶及摘要水位；官方來源與限制只見 REQ-002 第 9.1 節。
- 觸發門檻與保留區納入本包集中 context 政策，按完整 request 的可取得 token 用量／明示估算及指定模型能力判斷，不把每輪都摘要或填滿 128k 當目標。先保留完整 native function call／response 配對、仍需用的原始證據／來源位置與版本、未解決操作及收據、授權／撤權與 review 綁定；壓縮不能把不可信內容、模型推斷或未核草稿升格為系統指令、用戶同意或已核准事實，摘要也不是可取代原文的引用。
- summarizer 必須經相同受控 gateway／付款身份及 root 或原工作總帳計入模型嘗試、tokens、重試與期限，保留審核／修訂／再審及收尾餘額；確認取消／撤權可阻止未派發工作，已發出但取消未確認不報已停止。不得直接接入一個繞過本項目計量、授權或 abort 管理的原生模型。
- 摘要失敗、無效、逾時或餘額不足時，不丟原事件、不推進 coverage／摘要水位、不產生假成功；原上下文仍符合完整 request 邊界才可沿用，否則以可恢復的明確狀態停止或要求有界補讀，不截掉安全條件後硬送。重試仍受原總帳及停止條件約束。
- 接入前驗證 compaction event 的持久格式／重啟相容、原事件追溯及按需補讀、身份／孩子／模式隔離、取消與失敗回退。以合成 provider 檢查壓縮觸發、計量與保護內容不變；它不證明真模型摘要品質或效能提升，必要的真模型對照仍須另有批准及有界預算。

背景較長延後接續可先以 **1／5／15／60 分鐘**作排程例子，依錯誤、`Retry-After`、總帳及版本狀態調整；這是待測產品策略，不是官方固定間隔或永續模型重試。必須區分同一次請求的技術重試、保留成果後的工作接續，以及需維護者處理的永久故障。

## 6. 費用示例與尚未批准的財務邊界

以 Gemini 3.1 Flash-Lite 的 [Gemini Developer API Standard 價格](https://ai.google.dev/gemini-api/docs/pricing)作示例：文字輸入 US$0.25／百萬 tokens，輸出（包括 thinking）US$1.50／百萬 tokens。這不是 Vertex／non-global 路徑同價的保證，亦未核對使用者實際帳戶帳單。

- 假設一次生成為 32,000 input＋8,000 output tokens：`32,000 ÷ 1,000,000 × 0.25 + 8,000 ÷ 1,000,000 × 1.50 = US$0.02`。
- **僅在每次皆符合上述同一假設時**，64 次約 US$1.28，2,000 次約 US$40；不是固定每次成本、每輪／每日硬金額上限，也不是已批准花費。
- 實際輸入長度、輸出與 thinking、重試及快取會改變費用；示例未包括 embedding、搜索、儲存、網絡及其他服務。2,000 次若混有其他用量種類，亦不能直接套生成單價。
- 平台、公共維護及個人出資方的貨幣預算尚未定，必須由各 owner 明確設定並投影有效餘額／告警；不得把數量上調提案視作財務授權。

## 7. 全鏈調整，不只改環境變數

- 依附件逐項追蹤實際路徑：shared policy／schema → saved policy／舊版本相容 → gateway／各 provider → 工具及回答格式 → UI 有效值 → 持久 attempts／events／收據 → claim／lease／worker → dispatch／HTTP／SSE → daily／貨幣總帳。
- 明確處理現有 1,024 output clamp、schema／context 回傳牆、持久 attempts／ADK events 容量，以及早於 root 的 claim／外層期限；不能只把 `.env` 設大、其他層仍按舊小值拒絕。
- 單次、整輪、背景接續、傳輸接收及 lease 是不同期限；提高其中一項時驗證外層仍有正確續租、取消、查回與容量安排，不誤把 Node request 接收期限當整個模型執行期限。
- 政策更新有版本與相容遷移，舊資料的缺省／clamp 不得偷偷蓋過新值；UI 說明實際限制來自供應商、本人、平台、共享容量還是舊版待遷移。
- 持續貼線由維護者診斷設計、重複工作、上下文、來源品質、供應商故障或真實重負載，不武斷把所有峰值當 bug；也不只無限加額掩蓋循環。

## 8. 累積資料：取消小型總量牆，保留真實容量管理

- 50 份 active 文件、50 項私人來源、200 項關注、摘要全域 2,000／區間 200 筆等小型業務總量牆不應成為長期使用的常態終點。目標是可擴展資料處理，不只是把 50 換成另一個更大固定數字。
- 按授權範圍、時間及必要索引查詢，使用穩定分頁／cursor、去重與必要計數；區分畫面單頁大小、搜尋候選量及真正總容量，不一次把全部歷史載入記憶體或模型。
- 統計採必要的增量／聚合或授權後分批計算，保留正確更新及失效；加密資料須沿既有授權解密／統計路徑，不為方便查詢把敏感內容另存明文索引欄位。
- Firestore 原生[查詢游標](https://firebase.google.com/docs/firestore/query-data/query-cursors)及[聚合查詢](https://firebase.google.com/docs/firestore/query-data/aggregation-queries)可作既有能力參考；它們不會自動替加密正文計算所需業務統計，亦不免除索引、查詢範圍及成本驗證。
- 報告若稱全量統計、完整匯出或備份，須有可接續、固定一致範圍的 manifest、批次狀態、數量／hash 核對與完整完成標記；部分完成明示，不因達某頁／物件限額而截斷後宣稱完整。正文選錄與完整原始資料匯出分開。
- 備份／還原與大型資料處理不能略過完整性及版本檢查；遷移期間保留恢復方式，不能以提高容量為理由執行未批准的真還原或不可逆清理。
- 儲存的真實成本、容量、清理積壓及共享 Server 承載仍需集中可調與維護者預警；可擴展不等於無限免費儲存，不暗中刪除使用者原資料來避開限額。

# REQ-006｜模組化來源庫、共享匯入匯出與分類精細度治理

## 1. 已確認方向

- 知識資料按來源模組化管理，**機構／來源名稱是第一分類**，不把不同來源混成一堆內容。[家庭健康服務網站](https://www.fhs.gov.hk/)仍可作來源卡示例；本版明確補充：不是「每站必一庫」、一頁一庫或「政府」一張卡吞下所有旗下網站，亦不表示已抓取全站。
- 在既有「記憶與參考」**同一頁面展示多個資料來源庫卡片**，讓使用者看見採用了哪些機構／來源、各自範圍與完整性／有效版本；主題及來源性質標籤只用作篩選，不拿標籤來切卡，不另建大型插件或通用權限平台。
- 每個庫可獨立匯入、匯出及分享可合法分享的公共成果，讓其他人復用已整理內容，減少同版本重複的個人消耗；不承諾完全零成本，也不混入任何家庭私人資料。
- 按用途與資料價值決定精細度，不對所有內容一刀切逐句向量化，亦不以低使用率直接判定無用。

## 2. 卡片、分類與穩定來源身份

- 一張卡代表某機構／來源下**可獨立管理的資料庫或資料系列**。單一小站可一張卡；大型機構／網站按內容系列、使用目的、範圍及更新／維護責任邊界合理拆分，保留共同機構分類。不是因頁數／文件數到某個固定門檻就拆，也不因主題標籤、parser 不同而硬拆；一卡可有多個子分類、文件及讀取設定。
- 同一文件可符合多個篩選標籤，底層仍以穩定來源／文件／版本身份去重，不為每個標籤複製一庫。同站長期手冊與新聞／召回可採不同政策；是否分卡由獨立管理邊界決定，不把整站硬歸同一時效類別。
- **建議呈現**可區分長期資料庫、動態更新庫及即時搜尋來源，但這是狀態／性質呈現，不推翻機構／來源第一分類。即時搜尋來源尚未收錄的內容要明示，不把「可以搜索此站」冒稱整庫已讀取或已保存。
- 卡面顯示卡片名、機構／來源、登記範圍、最近成功更新時間、目前狀態及啟用情況；最後檢查與成功更新分開，檢查失敗不能刷新成功時間。展開可看子分類、文件清單、原網站、版本、缺漏、讀取方法驗證狀態、自建／匯入來源及匯出設定。
- 提供查看、更新、啟用／停用、匯入、匯出等必要操作；進度／錯誤沿 REQ-004。同時分清來源已接入、原文已讀取、成果已處理／發布、某次回答實際引用及部分收錄，不把接入卡片、少量搜索結果或局部處理當整站完整。
- 來源庫、網站／發布者、文件版本與片段有穩定身份，**不以顯示名稱、標籤或分類路徑作唯一 ID**。改名、移動分類不是新建來源庫；版本升級、合理拆卡／合卡保留舊身份映射及引用追溯，不靜默複製內容或破壞歷史證據。
- 跨庫檢索可合併整理，但保留來源差異、日期、適用範圍及相互矛盾。本人停用與刪除全體共享內容分開，不影響他人；解除 reference 及回收仍依被使用的版本和保留政策。

### 2.1 聊天引用沿用卡片名，先看本次證據再開原文

- 聊天答案下方的引用名稱直接沿用相應來源卡片名，由同一來源身份解析，避免聊天與來源頁各有一套不相干名稱。顯示名稱不代替實際證據 ID；引用仍能沿「卡片／來源庫 → 子分類 → 文件版本 → 頁碼／段落」追溯。
- **第一擊展開本次引用的證據**：所屬子分類、文件名稱、簡短原文、PDF 頁碼／段落及版本日期，優先定位本次答案真正用到的文件，不先把人丟進全庫分類迷宮。另設查看整個來源庫的入口；簡短不代表省略影響理解的條件、單位或相鄰上下文。
- **第二擊文件或「查看原文」才跳轉原始 URL／PDF**；支援時定位到相應頁／段，不支援時仍保留可見頁碼與文件定位資訊，不承諾所有外站都可深連結。原文沒有公開入口、已失效或需權限時，明示狀態及可用的合法定位／留存證據，不編造連結、不繞過存取限制。
- 同一卡片引用多份文件可合併為一個入口，但展開後逐份列出本次證據，保留每個陳述對應的文件、版本及位置；不能把卡片名當成「整庫都支持答案」的背書。短原文須是真實節錄；翻譯、摘要或模型解釋另行標示，不冒充原文。
- 引用保存回答當時的來源／卡片 ID、名稱快照、文件版本、位置及合法可保存的證據。庫升版、改名或移分類不得把歷史原文偷換成最新版；如顯示現行卡片名，仍保留當時名稱與版本供核對。來源撤回／失效需提示，但不重寫當時引用成另一份內容。分享與查看均保留原有權利及私人讀取隔離。此處的持久引用留存適用主聊天等允許保存的範圍；臨時會話的引用及其對話連結仍沿 REQ-003 於退出清除，不為保留歷史引用而例外持久化。

### 2.2 即時搜索沿同一命名與兩步引用，不強制建庫

- 尚未建庫的即時來源亦沿同一**機構／來源名稱＋必要範圍**規則顯示引用名；有現成來源卡時復用其名稱，沒有卡時由實際來源資料給出可讀名稱。不同 query 的名稱有少量變動可接受，不為字面統一另建龐大命名系統或額外模型流程；歷史引用保留當次名稱快照，不被後來名稱微調改寫證據。
- 即時來源可使用本包相同的兩步引用：第一擊看本次來源／可辨子分類、文件、短原文及可取得的頁碼／日期／版本，第二擊開實際原文。沒有既建分類／版本時如實標示，不為湊欄位杜撰；**不因產生引用就強制建立持久來源庫、訂閱更新或整站入庫**，查看全庫入口只在確有對應庫時提供。
- 引用按鈕以適度顏色變化區別**本次證據來自即時搜索**，並輔以「即時搜索」文字／圖示等非色彩線索；具體配色待設計，不以顏色單獨傳遞意義。同一來源可既有庫版本又被即時查詢，區別的是本次證據取得方式，**不是以顏色暗示官方／社群可信度或已通過審核**。
- 引用證據保留實際 URL、文件身份、取得時間、原文位置及可取得的版本／日期，缺項明示；主聊天依原保存規則保留當次證據，不偷偷換成下一次搜索內容。臨時會話的引用證據及對話關聯只在當次範圍使用，退出按 REQ-003 清除；公開原文快取與臨時私人查詢分開，外部 query 最小化沿 REQ-001。

## 3. 兩種導入路徑

### 3.1 從網站建立來源庫

- 使用者提供網站後，Agent 按已允許的網域、路徑、內容類型及完整範圍取得原文，交 REQ-004 的解析、整理、核對及發布流程，形成可管理的庫。
- 網站範圍若未明確，先固定可處理範圍，而不是把輸入首頁視為無限跨站爬取授權；不繞登入、存取、機器擷取或使用方式限制。
- 已納入的整本 PDF 自動處理全本；對網站登記的文件／頁面集合有完整 manifest、缺漏及後續接續，不能只保存搜索前幾項便宣稱整庫完成。
- 來源選定、scope 與可使用方式確認完成後，正常更新由系統進行，不要求家長每批批准。擴大來源範圍與日常在既有範圍內更新是不同決策。

### 3.2 匯入他人已整理的庫

- 復用對方可分享的原文位置、整理結果、分類、版本與可相容索引，不預設全部再跑一次模型；先做格式、完整性、來源、hash、相容性及必要內容可信度檢查。
- 匯入包是外部資料，不是系統指令或權限。包內自稱「已核准」、附簽名或帶 approval 欄位，不足以跳過本系統的來源／核對要求；簽名如有，只能在信任關係成立時證明相應身份／完整性。
- 來源可信度不能因匯入而升級：轉載／社群資料仍是轉載／社群，不能標成官方原始指引。核對證據不足時保留待驗狀態，不默默進正式答案索引。
- 已有證據可復用，必要驗證只處理缺項／風險／變更範圍；不是無差別整庫重做 LLM。具體可接受證據、抽查／獨立審核條件及成本邊界在實施前固定。

## 4. 可攜封裝與公共共享版本

- 匯出包在既有內容／成果封裝上，亦可包含**已驗證的讀取方法**：格式版本、完整 manifest、穩定來源／庫 ID 與版本／範圍、provenance、合法原始材料或取得位置、處理成果、引用位置及 hash、分類政策版本、必要索引描述，以及可分享的來源發現／擷取／差異判斷設定。
- 讀取方法須帶驗證時間、適用網站／格式／範圍、可分享的代表樣本或樣本定位／hash、預期欄位與完整性測試、所需 parser／OCR 等能力及版本依賴、已知限制。方法驗證不是永久有效保證，亦不自動等於整庫內容已經審核。
- 匯入時先核宣告式設定格式、能力／版本相容、來源範圍及依賴，再按既有授權做小量讀取與樣本／完整性驗證；未具備依賴或不能訪問時明示待驗，不為通過而擴權或下載執行任意程式。必要模型驗證另受預算與批准邊界限制，不盲信對方「已驗」旗標。
- 外部包只可描述受支援的讀取設定，**不任意執行匯入程式、shell、動態腳本或把其提示升為系統指令**。過時方法可替換／修復並重新驗證受影響範圍，原文及仍有效處理成果不必推倒重做；不保證跨環境零成本或永遠無需重新讀站。
- 向量如可分享，須帶模型、維度、向量空間及切段／索引版本等相容資訊；相容時復用，不相容時只重建所需索引／向量，不把重索引宣稱零成本，也不無故重新整理未變原文。
- 匯入／匯出可分批，但以 manifest 驗完整、查缺漏、去重並可接續；部分包不能冒充完整來源庫。損壞、hash 不符或不支援格式有明確拒絕／待修狀態。
- 相同公開來源及內容版本可共用不可變的成果 reference，避免每人重複保存／處理。每位使用者的選用、啟停及升版選擇獨立，不因他人設定而改變自己的庫。
- 個人 key、帳戶授權／憑證、孩子資料、聊天、私人記憶、家庭內容及個人預算不得進公共索引或來源庫分享包；讀取設定及樣本亦須檢查，不能夾帶登入資料或本地私人路徑。公共封裝採明確欄位白名單與輸出檢查，不從整個帳戶直接打包；匯入設定不能覆蓋接收者的權限或資源政策。
- 只分享符合來源條款及權利允許的內容；原文不能轉發時，不以「大家共同使用」作理由複製，而按允許方式分享連結／metadata／可分享成果並明示缺少的原文。
- 公共庫後續更新與私人匯入快照是不同生命週期。私人匯入是固定版本，還是可選擇跟隨上游更新、如何驗證來源與通知升版，列為待定；不能暗中替所有人自動跟隨或把私人包上傳成公共庫。

## 5. 按類別與用途控制精細度

以下四類是**處理策略建議**，不是新的來源可信度等級；同一文件可同時包含多種內容。

| 處理策略 | 適用內容及要保留的意義 | 不應做的事 |
|---|---|---|
| 精細保留 | 數字／單位、照護步驟、年齡／適用條件、安全警示、禁忌與例外；保留原文及必要相鄰上下文 | 不能只存概括摘要、切掉條件或憑低使用率刪掉重要例外 |
| 概括整理 | 背景介紹、重複解釋或一般脈絡，整理足以支援理解並保留原文入口 | 不把概括內容用作更精確的數字、診斷或個別建議依據 |
| 結構化保存 | 日期、有效期、批次、型號、事件狀態、地址等需要精確比對的欄位 | 不只靠向量相似度猜日期／批次，不丟來源位置及更新狀態 |
| 不進問答索引 | 裝飾、重複導航、宣傳或與登記用途無關內容，在完整覆蓋中記錄分類理由 | 不索引不等於刪原文；不把讀不清／未處理內容偽裝成無關 |

- 原文層、整理層與檢索索引層分開；完整來源覆蓋由 REQ-004 管，是否精細處理或索引由本包的用途政策管。
- 精細度按代表問題能否命中正確內容、條件是否完整、噪音／重複及處理成本量測，不以固定字數或平均每頁向量數作唯一標準。
- 低查詢次數只是一個觀測訊號，不等於無用；低頻但重要的安全例外須保留。使用者私人原資料不得因系統判定「價值低」而自動刪除。
- 以少量可理解的類別政策作預設，必要時加少量 source override；政策版本化、可調及可回溯，不把每個網站／文件的規則散寫成常數。
- 政策變更只重處理受影響範圍，重用原文及仍相容成果；分類改動、重新切段與索引失效要可追蹤，不每日整庫重跑模型。

## 6. 建議實施階段與驗收

| 階段 | 工作與依賴 | 交付門檻 |
|---|---|---|
| 0．身份與政策 | 與 REQ-004／005 固定機構／資料系列／卡片邊界、穩定 ID、文件版本、manifest、讀取設定、引用快照及原文／索引分層 | 分類／改名不換 ID，標籤只篩選，私有／公共及方法／內容驗證邊界清楚 |
| 1．來源庫核心 | 沿既有來源／知識服務建立獨立模組、版本 reference、跨庫查詢及來源追溯 | 不混來源、不重複處理相同版本，個人啟停不影響其他人 |
| 2．頁面、引用與網站導入 | 在「記憶與參考」同頁按機構／來源呈現多卡，接入範圍及 REQ-004 狀態；聊天引用同名，兩步查看本次證據／原文 | 大來源可按系列管理，部分收錄不假完整；第一擊定位證據，第二擊跳原文，歷史版本不被更新偷換 |
| 3．可攜封裝 | 單庫內容及已驗讀取設定一併匯出；匯入核格式／hash／provenance／依賴，再小量樣本驗證，復用相容成果 | 不執行任意外部程式、不盲信核准旗標、不帶私人資料或個人預算；方法可修復，部分包不報完整 |
| 4．分類校正與共享更新 | 用少量代表問題衡量精細度、噪音及成本；固定匯入快照／跟隨上游的產品選項 | 只重處理受影響內容，公共更新與個人選擇獨立，來源可信度不被升格 |

| 驗收場景 | 應驗證的結果 |
|---|---|
| 小站、大機構及同站多系列 | 以機構／來源為第一分類，小站可一卡、大來源可按獨立管理系列分卡；不以「政府」吞所有站，不按文件數、標籤或 parser 硬拆 |
| 多標籤與一卡多讀取方法 | 篩選不複製來源／文件，單卡可使用多套方法，同站長期／時效可採不同政策 |
| 記憶與參考單頁卡片 | 名稱、機構、範圍、最近成功更新、狀態及啟用可讀；展開看到文件／方法／版本／匯出設定，檢查失敗不冒充更新成功 |
| 即時搜尋及部分收錄 | 明示可搜索、已接入、已讀取／處理、發布與實際引用差別，不將接入或局部收錄報成全站完整 |
| 未建庫新網域首次即時搜索 | 沿機構／來源＋範圍命名，第一擊直接看本次證據、第二擊原 URL；無持久庫／訂閱／整站收錄也可引用，缺少分類或版本不杜撰 |
| 同來源庫引用與即時引用並存 | 按本次取得方式區分，顏色配合文字／圖示可辨，不只靠色彩、不當可信度或核准等級；跨次小幅改名不偷換舊證據 |
| 即時引用的版本與臨時退出 | 主聊天可追溯當次 URL／文件／取得時間及可用版本；臨時會話退出清除其引用與對話關聯，不因引用保留例外而回寫主庫／主聊天 |
| 導入含整本 PDF 的來源範圍 | 自動完成登記範圍或明示缺漏；不以幾頁／前幾項搜索結果冒充完整 |
| 相同公共版本由兩位使用者使用 | 可復用成果 reference，各自啟停／升版互不影響，不重複個人模型消耗作假共享 |
| 聊天引用第一擊／第二擊 | 引用與卡片同名；第一擊顯示本次子分類、文件、短原文與頁碼／版本，第二擊才跳原文；Web／手機操作及可讀名稱一致，有對應來源庫時另有全庫入口 |
| 同卡多文件、跨庫矛盾與翻譯 | 逐份證據及陳述對應不丟失，日期／適用條件與差異保留，翻譯摘要不冒充短原文 |
| 改名、移分類、拆合及升版 | 穩定 ID／映射可追溯，舊回答仍指當時文件版本與位置，不偷換成新版原文 |
| 原文失效、非公開或無頁面深連結 | 如實提示，保留可用合法定位及頁碼，不造連結或越權讀取 |
| 單庫匯出／匯入中斷、損壞或缺件 | manifest 查完整性並可接續；未完整不標完成，損壞有明確處理結果 |
| 匯入包自稱 approved、含程式或指令 | 不取得系統權限、不執行任意程式或跳核對，來源不因匯入變官方 |
| 帶已驗方法的包在新環境匯入 | 讀取設定／驗證範圍／樣本／依賴可讀，小量相容及完整性驗證過後才啟用；過時方法可修而不推倒有效內容 |
| 向量相容／不相容 | 相容成果可復用；不相容只重建必要索引並明示成本，不整庫重做語義整理 |
| 分享包的私人隔離 | 內容、設定及樣本不含孩子、聊天、記憶、憑證、key、帳戶授權或個人預算；私人包不自動變公共，匯入不改接收者政策 |
| 細節分類及低頻安全例外 | 數字／單位／條件完整，重要例外保留，裝飾／重複不製造大量噪音 |
| 政策變更／停用 | 只重處理受影響範圍；不索引或本人停用不等於刪原文／全體共享內容 |
| 匯入庫後續版本 | 固定快照或跟隨上游選擇明示，不暗中更新、擴大範圍或分享私人內容 |

## 7. 待決事項與整體接續順序

待決：首批機構／網站／資料系列邊界與文件範圍、卡片及現有服務映射、拆合身份相容與引用快照保存方式、短原文合法長度／留存及外站定位支援、四類策略預設與 override 權責、可分享權利及內容／讀取設定封裝格式、驗證樣本／依賴相容／外部證據補驗策略、向量相容定義、公共成果出資與儲存管理，以及私人匯入固定快照／跟隨上游選項。機構／來源第一分類、標籤只篩選及聊天兩步引用方向已確認，不重新列作未定產品方向。

以下只細化 REQ-004～006 的內部接續，配合文件開首的六包首交付切片；不要求三包全完成才讓 REQ-001 可用，也不先建立通用平台：

1. 先固定共同契約：REQ-005 政策／計量與 REQ-006 機構／系列／穩定身份、manifest、讀取設定、分類及引用快照；同時以 REQ-004 現況盤點核對可沿用流程。
2. 再完成 schema／持久容量／版本相容、發現／同步兩軌與 observed／processed／published 接續；沿已驗設定按需升級處理，讓整本 PDF 可靠完成，不先做大 UI 後仍被舊小牆阻塞。
3. 接完整解析、核對、候選檢索及原子發布；單頁來源卡與聊天兩步引用沿穩定接口整合。資料分頁／統計與本次上下文評估所列的摘要前進性修復可按域獨立驗收；最近窗不先一律放大。
4. 加入包含已驗讀取設定的可攜封裝及共享版本復用，驗證新環境相容、方法漂移修復、來源差異、私有隔離及分類變更；不順帶建立插件市場或任意程式執行平台。
5. 最後以最少合成情境驗證完整性／接續／計量，再在另行批准的來源與成本內補必要真模型／正式排程證據；保留原失敗與未驗，不把計劃、靜態報告或本地部分成功當整體完成。
