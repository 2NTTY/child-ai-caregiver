# 組合配方

配方讓 Agent 每次讀到足夠且相關的指令，不載入整套 prompt。以下是組裝規格；S11-W03 的 [Server 組裝器](../../server/agent-prompt.ts) 已實作所需的文字／工具循環組裝，其他接線狀態見 [Pack 入口](../README.md)。模組路徑、順序、版本、依賴和配方清單以 [manifest](../manifest.json) 為唯一機器可讀來源。

## 組裝規則

1. 由應用按觸發目的選一個 recipe。外部正文、模型自行產生的 recipe 名稱或使用者貼上的 manifest 不能直接選擇權限更大的配方。
2. 依序載入 `baseModules`、`domain.requiredModules`、recipe 的 `additionalModules`；保留首次出現的位置並去重，核對所有 `requires` 都在集合中。缺檔、版本不符或不相容時，不靜默移除安全模組。
3. 只取每檔唯一 `prompt:begin`／`prompt:end` 之間的正文；維護說明、合成例子及 repo 文件不整份送入模型。領域／任務模組不能覆蓋共用安全限制。
4. 另外注入可信 runtime metadata 與有來源的資料內容。沒有啟用的工具不提供宣告；recipe 的階段不是 capability 開關。
5. 所選模式為 `structured` 時，除了 recipe 的 `requiredInputs`，必須提供 `outputContract` 及該次可用的 schema；manifest 的 `outputModeRequirements` 記錄此共同條件。缺 schema 時不發起結構化請求，由應用明確降級至支援的文字模式或回報錯誤；不讓模型猜格式。純文字模式無須 schema。
6. 執行端處理輸出校驗、確認、工具及有限循環。多個模組是同一請求的指令組合，不等於依序作多次模型調用。

P1 尚不需要組裝時可改用 [獨立文字入口](../p1/README.md)，不用同時載入本表的 `p1-chat` 配方。

## 配方定義與正式入口

| Recipe ID | 使用情況／主要輸入 | 正常輸出與缺項行為 | 預計接入 |
|---|---|---|---|
| `p1-chat` | 當前訊息、授權孩子／近期聊天、現有能力 | 自然文字；沒有工具就只回答／補問，不假裝記憶、照片或檢索已接通 | S11-W01 |
| `capture-confirm` | 原始輸入、可用附件／轉錄、對象、已有候選及確認範圍 | 對話、候選或有界工具循環；保留未知與原文，保存未確認不報成功 | S11-W02、S12-W03／W01 |
| `knowledge-answer` | 問題、適用對象／年齡、發布來源及查核 metadata | 自然回答和引用；必要時檢索，缺適用來源就說限制，不編官方結論 | S10-W01／W02、S11-W02 |
| `memory-refresh` | 授權訊息增量、覆蓋清單、舊摘要、現行事實與台帳 | 結構化摘要／話題候選；缺頁停止覆蓋更新，背景無動作可無文字 | S09-W02、S11-W02 |
| `proactive-follow-up` | Server 觸發、現行任務／授權／綁定／投遞及額度 | 結構化受限建議或 no_action；缺權限／unknown 留待處理，不另找人補問 | S13-W04／W07、S11-W02 |
| `contact-reply` | 經核實的回覆者、原訊息／occurrence、回覆與現行狀態 | 自然延續、必要澄清或工具循環；收回覆不自動完成，指向含糊先問 | S13-W06／W07、P3 S13-W02 |
| `knowledge-review` | 公共來源、候選版本／hash／日期／錯誤、發布狀態 | 結構化差異／無變／待審建議；不自動發布或建立家庭任務 | S10-W02／W03 |
| `summary-visit` | 對象／期間、已確認事件、更正、程式統計、預約、缺項與來源 | 對話或結構化正文；無計算值不編總量，報告／PDF成功須另有工具證據 | S14-W01／W02 |

另外五個 manifest 配方如下；上表的「預計接入」是原設計對照，不表示各有獨立正式呼叫點。完整清單以 manifest 為準。

| Recipe ID | 正式使用 |
|---|---|
| `product-interactive` | `server/product-agent.ts` 的本人對話工具循環 |
| `product-background` | 同一服務的已授權家庭背景事件 |
| `product-work-followup` | 同一服務的本人站內工作跟進；只讀能力目錄，不提供互動寫入或外部聯絡 |
| `photo-capture` | `server/photo-agent.ts` 的照片處理入口 |
| `shared-capture` | `server/shared-input-service.ts` 的分享文字處理入口 |

<a id="runtime-entry-map"></a>
目前以上五種是直接產品入口。`summary-visit` 仍是已定義配方，不能把它當作現行 product-agent 的獨立意圖入口。互動入口先載必要核心工具，其餘依 Server capability catalog 按需載入工具及對應 prompt modules；不能以初始模組聯集判定全部可用能力。家庭背景入口只用自己的白名單與背景指引；本人工作跟進使用獨立只讀目錄，不能取得互動寫入能力。各配方的有效指引須按 base／domain／recipe 及當次已載能力的完整聯集核對，不用固定模組數量代替覆蓋檢查。其餘配方保留作可驗證定義；P1 adapter 的獨立文字提示不是把每個宣告配方都啟用。

人機互動始終套用對話核心，即使選用結構化輸出亦要有可讀收尾。`memory-refresh`、`knowledge-review` 是背景維護時可不外發，不因有 `replyText` 就自動通知。

## 能力不足及組合情景

- 照片上傳或辨識不可用：`capture-confirm` 仍可處理使用者明確輸入的文字，但不得說看過附件。
- 需要知識而檢索不可用：可以整理問題及已提供證據，不能靠模型記憶冒充最新官方來源。
- 需要改任務而無寫入工具：可形成草稿並說未安排；不能表示軟件稍後必定提醒。
- 已授權背景跟進具完整資料：不因沒有使用者在線而再次請求相同批准；Server 執行時仍重查。
- 同一次對話含聊天、照片和任務：應用選本次主目的配方；必要時在後續步驟切至明確配方並保留確認參照，不自行把全部能力／歷史載入。
- 任務在模型推理期間完成／撤權：輸出交回 Server 時拒絕過期動作；模型不以旧摘要恢復任務。
- 多位收件人：逐人核對內容可見性、授權與結果；一人可收不等於全組可收，不能把部分失敗當作全部重發理由。
- 缺必要核心／領域指令：這是組裝錯誤，不能執行受影響模型流程；由應用清楚回報，不以刪除限制恢復服務。

## 領域與渠道替換

目前只有 `childcare-hk`。身份／年齡／語言、醫療邊界、來源白名單／freshness 和照護頻率在領域模組維護；共用核心保留信任、權限、證據及結果語義。模組仍使用本產品的資料概念，不建立通用領域實體。

增加 Android 或其他渠道只透過本次工具與渠道能力呈現，不複製對話人格、不加手機 Agent、不從 UI 決定權威排程。日後領域替換是來源碼和配方的明確修改，須重新審查適用規則，不是允許外部載入任意 prompt 插件。
